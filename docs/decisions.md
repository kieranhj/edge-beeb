# Decisions of record

The table every deviation from the C64 original, and every choice the hardware forced, gets a row in.
Per-layer detail lives in that layer's `docs/layer-*.md`; this is the index. Nothing here is
re-litigated without a new row saying why.

| # | Date | Decision | Where |
|---|---|---|---|
| 1 | 2026-09-02 | **Target is the BBC Master 128 only.** The 1-pixel scroll needs two full 16K screens inside a hardware wrap region (main and shadow RAM at `&4000-&7FFF`), which a Model B cannot provide. Paradroid costed sub-4-pixel scrolling on a B and rejected every option. A B+128 has shadow RAM with different paging and is not planned | `PROPOSAL.md` §2 |
| 2 | 2026-09-02 | **Sprites are clipped at the play-area edges, not culled.** Enemies enter from the right and the bullet leaves it; Paradroid's whole-sprite cull would make them pop. Edge culling is the fallback only if clipping cannot fit the frame budget | `PROPOSAL.md` §3.7 |
| 3 | 2026-09-02 | **Hand-authored MODE 2 art is a free redraw inside the existing tile boundaries.** All eight colours, gradients and fat-pixel dithering; tile outlines, the 4 × 4 character grid, the 211 tile definitions and the map stay the C64's. `reference/beeb-artwork-example.jpg` is the target look | `PROPOSAL.md` §5.2 |
| 4 | 2026-09-02 | **Art is exchanged by shared folder or email**, mirrored into `assets/` by a script; we commit. No git on the artist's side | `PROPOSAL.md` §5.2 |
| 5 | 2026-09-02 | **Music is converted automatically from the CPC Arkos tune** with the nova-invite toolchain (`Repos/nova-invite/bin`: Arkos Tracker 2 → `SongToYm.exe` → `ym2sn.py` → `vgmpacker.py`, played by `lib/vgcplayer.asm`). Not a commission | `PROPOSAL.md` §7 |
| 6 | 2026-09-02 | **Keep the 2019 scroll scheme**: two phase-offset shadow screens, one byte column per frame through a 160-byte column buffer. It is the CPC's tile writer and it works at 1 px / 25 Hz. Paradroid's tranche split and window A/B scheduling are *not* adopted; they exist only because Paradroid is single-buffered | `PROPOSAL.md` §1, §3 |
| 7 | 2026-09-02 | **Sprite engine v2 follows Paradroid's model**: slot table, save area mirroring screen geometry, mask derived from the data byte (transparent = logical 0, black inside sprites = logical 8), two pre-shifted copies, deferred-carry `SCANSTEP`, restore replays the draw. Only the player and bullet are compiled; enemies are interpreted with bounding boxes | `PROPOSAL.md` §3 |
| 8 | 2026-09-02 | **The status bar is a CRTC rupture** (panel cycle at a fixed address below `&3000`, play cycle at the scrolling address), lifted from Paradroid's `rupture.asm` with its register-window rules. Not MODE 7 mixing | `PROPOSAL.md` §4 |
| 9 | 2026-09-02 | **Layer 0 keeps the binary identical.** The source split, build script and `!BOOT` change nothing in `Edge` or `BANK0`; verified by extracting both files from the old and new disc images | `docs/layer-0-toolchain.md` |
| 10 | 2026-09-02 | **`bin/` is gone.** `convert_sprites.py` was an unfinished stub (syntax errors) that the old `make.bat` ran and ignored; `bbc.py`, `png.py` and `png2bbc.py` were not part of the build. New tools go in `tools/` and use Pillow. The old files are in git history (commit `53af281`) and `bbc.py`'s MODE 2 packing survives in `Repos/nova-invite/bin` | `docs/layer-0-toolchain.md` |
| 11 | 2026-09-02 | **C64 → BBC colour table for the mechanical conversion** (`tools/bbc.py` `C64_TO_BBC`): the eight saturated colours map to themselves; brown (the playfield's shared `$d022`) → blue as the 2019 port chose; orange → red, pink → magenta, dark grey → blue, light green → green, light blue → cyan, greys → white. For the mechanical pass only; the artist's redraw replaces it | `docs/layer-1-graphics-pipeline.md` |
| 12 | 2026-09-02 | **Characters are stored as four MODE 2 column planes** (8K) rather than plain 4 bpp, so the column buffer ORs a plane byte straight in. That fills bank 0, so sprite data lives in bank 1 (slot 5) and `plot_sprite` pages it in; bank 0 is the resting state | `docs/layer-1-graphics-pipeline.md` |
| 13 | 2026-09-02 | **The sprite plotter keeps reading raw C64 data until Layer 3.** `sprites.bin` is exported now (format may change) but rewriting the 2019 plotter for it, then again for the Layer 3 engine, was not worth it | `docs/layer-1-graphics-pipeline.md` |
| 14 | 2026-09-02 | **The map wraps at its true end (302 columns)** rather than at 256, in `map_read`. The C64 never reaches the end: its wave table raises the completion flag first, which Layer 5 will port; the wrap is only what happens until then | `docs/layer-2-display.md` |
| 15 | 2026-09-02 | **Two rupture cycles, not Paradroid's three**: panel (5 rows, the C64 height) then a 34-row cycle holding the play area and the VSync at the MODE 2 row. No R5/R8 because nothing scrolls vertically; R7 is a constant | `docs/layer-2-display.md` |
| 16 | 2026-09-02 | **The VSync IRQ owns the bank flip**: the loop parks the scroll address and a ready flag; the handler flips both shadow bits and takes the address only when `FRAME_LOCK` = 2 fields have passed. A 25 Hz floor that degrades by whole fields without tearing | `docs/layer-2-display.md` |
| 17 | 2026-09-02 | **The panel lives inside the shadow-switched region (`&3000`) and is drawn into both banks.** At `&2000` jsbeeb displayed it under both shadow states but b-em showed garbage on alternate frames: what the video fetches below `&3000` with the D bit set is emulator-dependent and unverified on hardware, so nothing displayed may live there. Cost: every HUD write goes to both banks. `&2000-&2FFF` becomes the Layer 3 sprite-save area instead | `docs/layer-2-display.md` |
| 18 | 2026-09-03 | **Each pixel shift gets its own 16K sprite bank** (slots 5 and 6), identical in layout, rather than one bank holding both. Both shifts plus the tables come to ~24K. The engine pages in the bank a sprite's x asks for, so every address in the blitter is the same either way, and bank 0 stays the resting state | `docs/layer-3-sprites.md` |
| 19 | 2026-09-03 | **Sprites are drawn by an interpreted, bounding-boxed blitter; nothing is compiled yet.** `PROPOSAL.md` §3.6 proposed compiling the player and bullet. Measured, eight interpreted sprites cost 49,236 of the 79,872-cycle frame and leave room for the game, so compilation waits until Layers 4 and 5 show the real load. **The premise is now in doubt**: that measurement was taken while `BUGS.md` #8 was skipping every sprite past x = 140, and `BUGS.md` #9 has the frame overrunning in play. Not yet re-litigated - a new row goes here if it is | `docs/layer-3-sprites.md` |
| 20 | 2026-09-03 | **The hit flash is a recolour table on the ORA site**, not a second inner loop and not stored flash frames. Eight patch sites repointed when the colour changes, so it costs nothing per byte. It assumes a sprite holds transparent, blue, white and one other colour, which the exporter asserts across all 119 C64 frames; hand-drawn art with more colours needs a table per colour | `docs/layer-3-sprites.md` |
| 21 | 2026-09-03 | **A sprite that straddles the end of the 16K buffer walks `bufp` per column, for the whole sprite.** A buffer row is 640 bytes and 16,384/640 = 25.6, so the wrap point is not row-aligned and a row's seven columns can stop being 8 bytes apart. One conservative test per sprite rather than Paradroid's per-row test: it catches about one sprite in eight and is cheaper than testing 21 rows on all of them | `docs/layer-3-sprites.md` |
| 22 | 2026-09-03 | **Sprites do NOT take the scroll's half-byte bank phase** (`SPR_PHASE_MASK = 0`), reversing the assumption in `PROPOSAL.md` §3.1. Both banks are drawn at the same origin and displayed at the same CRTC address, so a screen-space sprite stands still under both without an adjustment. **Unconfirmed on a display**: if a stationary sprite shimmers one pixel at 50 Hz the mask goes to 1 | `docs/layer-3-sprites.md` |
| 23 | 2026-09-03 | **The game logic ticks twice per display frame.** The C64's main_loop runs at 50 Hz on `sync_wait` and ours at 25, so one pass is two of its iterations. Ticking twice rather than doubling every per-frame constant keeps the original's numbers - 1 of x, 2 of y, 12 of bullet, the `scroll_x AND 3` grind gate - transcribing unaltered, and checks the bullet at each 12-pixel step, which is what makes its three-cell check airtight. ~1,600 cycles a frame | `docs/layer-4-player.md` |
| 24 | 2026-09-03 | **Background collision reads a character map we keep ourselves**, at `&04A0` in main RAM (KC). The C64 reads character codes back out of the screen it displays; we draw pixels, so `plot_char_y` files the code it already has in Y and `player.asm` reads that. 40 x 20, columns as a ring, same grid and same `col_decode` fatal nibble as the original. `&04A0-&07FF` is the language workspace: verified by a sentinel surviving 3,000 fields of the running game | `docs/layer-4-player.md` |
| 25 | 2026-09-03 | **`bullet_colls` guards two cases the original does not.** With no bullet its y is 0 and the C64 indexes 27 rows into a 24-row table; past column 39 it reads into the next row down. Off-screen nonsense there, an out-of-range read here, so both return "no collision" | `docs/layer-4-player.md` |
| 26 | 2026-09-03 | **The keys are Z/X left/right, K/M up/down, L fire** (KC). The C64 uses a joystick; `read_joystick` packs the five into a byte with `$dc00`'s bit order and polarity, so `player_manage` transcribes verbatim. Every internal key number is **measured** with OSBYTE 121 in a BASIC session holding the key, never recalled - Z 97, X 66, K 70, M 101, L 86 | `docs/layer-4-player.md` |
| 27 | 2026-09-03 | **The game-state block lives at `&0800`, not in the code image.** The C64 keeps the same block in its tape buffer at `$0340` for the same reason: RAM that needs no initial value costs nothing to put where the image is not. `&0800-&0BFF` is the MOS's sound, serial and soft-key workspace, ours with the MOS interrupt gone - verified by a sentinel across all four pages surviving 1,500 fields of the running game. Declared after the SAVEs and outside them, so none of it reaches the disc | `docs/layer-5-enemies.md` |
| 28 | 2026-09-03 | **The wave table and `anim_decode` are exported to bank 0**, not hand-copied into the image. The original writes them with symbolic constants (`left_1+up_1`, `enemy_10`), so `tools/export_waves.py` resolves them out of the source; 1,810 bytes of waves and 38 of `anim_decode`. `wave_read` is self-modifying code over the bank exactly as `map_read` is over the map, and bank 0 is the resting state the wave manager already runs under | `docs/layer-5-enemies.md` |
