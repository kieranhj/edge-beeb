# Layer 8 — graphics pipeline B: the artist's PNGs (2026-09-05)

`PROPOSAL.md` §5.2 asked for a path that lets a non-developer repaint the game.
This is that path. The characters, the sprites, **the status panel, the HUD font**
and **the palette** are read from PNGs in `assets/art/` now; the C64 and CPC conversions are still there, and are
what the PNGs were seeded from.

## What was built

`tools/art/` is the new package, and it exists because there were already two
art sources and this is the third:

| File | Contents |
|---|---|
| `palette.py` | `assets/art/palette.png` — the sixteen MODE 2 logical colours as RGB — and the RGB → logical mapping in both directions |
| `sheets.py` | the four sheets' geometry, and the reader/writer that turns a PNG into cells of logical colour and back |
| `pngart.py` | the exporter-facing interface: `characters()`, `sprites(n)`, `panel()`, `hud()` - deliberately the same four-function shape `tools/cpc/bbcart.py` presents for the Amstrad art |
| `mechanical.py` | the C64 and CPC conversions, lifted out of the three exporters so the seeder and the fallback path can call them too |

and five tools beside it:

| Tool | Does |
|---|---|
| `tools/seed_art.py` | writes the sheets and the palette from the conversion the game runs on today (`--cpc` for the Amstrad's, `--blank` for a redraw from nothing) |
| `tools/validate_art.py` | what a drop from the artist goes through on receipt |
| `tools/export_palette.py` | `palette.png` → `src/data/palette.asm`, the bytes `setup_display` writes |
| `tools/export_panel.py` | `panel.png` and `hud.png` → `panel.bin` and `hud.bin`; the C64 reading it used to do is `mechanical.py`'s now |
| `tools/render_bbc.py` | unchanged in purpose, but reads the palette file now instead of assuming logical = physical `AND 7` |

`export_tiles.py` and `export_sprites.py` take their art from the PNGs by
default, `--cpc` for the Amstrad's and `--c64` for the mechanical conversion
outright. **No new build symbol** — `RELEASE`, `MUSIC_AKL` and `GFX_CPC` are
still the three, and the PNGs feed the same `src/data/*.bin` the build already
INCBINs.

## The four sheets

Both at 2:1 — a screen fat pixel is 2 image pixels across and 1 down, which is
the aspect the Beeb shows and the scale `reference/sprite-sheet.png` already
used. `sheets.Sheet` carries the geometry and `validate_art.py` proves every fat
pixel is a solid block, so a stray half-pixel is an error with coordinates
rather than whichever half the reader happened to sample.

```
assets/art/chars.png    128 x 128   256 characters, 16 a row, cell 8 x 8
assets/art/sprites.png  192 x 336   128 slots,  8 a row, cell 24 x 21
                                    frames 0-118 are the game's
assets/art/panel.png    320 x 40    the status bar as a picture
assets/art/hud.png      128 x 8     16 slots, 13 used, cell 8 x 8
```

**The panel is a picture, not a sheet** (decision 61). It is 5 character rows of
40 on screen and it is painted that way, at the size it appears; the exporter
cuts it into the 200 sixteen-byte cells the runtime copies to `&3000`. Which is
possible only because a panel cell, a HUD glyph and a character are *the same
shape* — 4 fat pixels by 8 rows — so one `Sheet`, one reader and one
`pack_cell` do all four sheets.

**Characters are the paintable surface and tiles are not** (decision 58). The
211 tile definitions and the 302-column map are *index tables* shared verbatim
with the C64 and CPC ports, and the charset is reused about thirteen times over
them; painting the tile sheet would mean repeating every edit thirteen times.
`tools/render_bbc.py tiles` and `map` regenerate the assembled views instead, so
the artist sees his characters in the real level without them being the thing he
edits.

Two magic colours, neither of which may be a palette entry: grey `96,96,96` is
the transparency key (sprites only — the background is opaque) and orange
`255,128,0` marks a cell **not drawn yet**, which falls back to the mechanical
conversion. That is what makes a partial drop build a complete game, and it is
whole-cell-or-nothing: orange mixed into a painted cell is an error.

## The palette is a file

`setup_display` used to compute the palette — logical n → physical n `AND 7`,
with 8-15 aliasing 0-7 so logical 8 is a second black the sprite engine can use
(logical 0 being its transparency key). It reads sixteen generated bytes now.

An artist who paints a colour is painting a palette entry, so the palette and
the sheets have to be one thing that is checked against itself. Every pixel of
every sheet resolves through `palette.png` by **exact match**; an unknown RGB is
an error naming the sheet, the cell and the pixel. A nearest match is how art
quietly stops being what the artist drew.

`pal_data` is in **main RAM**, beside the loader above `code_end`, not in bank 0
with `setup_display`. Bank 0 had nine bytes left; the boot-only region above
`code_end` has hundreds, main RAM is never paged out from under bank 0, and
`setup_display` is boot code. Bank 0 gained fourteen bytes over the loop it
replaced, and `CODE CEILING` is unchanged.

## Planning ahead for NULA

The point of putting the palette in a file is that a NULA build then costs
almost nothing:

* **Nothing in the data formats changes.** `chars.bin` and the two sprite banks
  already store a full 4-bit logical colour per fat pixel — `mode2_byte` packs
  0-15 and always did — and the mask and flash LUTs work on nibbles.
* `export_palette.py --nula` already emits the other form: two bytes an entry to
  `&FE23`, `(logical << 4) OR red` then `(green << 4) OR blue`, each channel the
  top nibble. `setup_display`'s loop is `PAL_BYTES` long and needs no change.
* Entries 8-15 stop aliasing and become eight more colours. The artist goes from
  seven colours plus black to fifteen.
* **Logical 0 stays the transparency key under both.** `mask_table` keys on a
  zero nibble; that is not negotiable and the palette file's rules encode it —
  `lookup(sprite=True)` never returns 0, which is why black inside a sprite is
  logical 8 today.
* `render_bbc.py`'s `AND 7` is gone, because that assumption is exactly what a
  NULA breaks.

**What a NULA build would still need**, and is not built:

* the palette register write itself (`&FE23` and NULA's enable sequence), and a
  build symbol to choose it;
* **the two palette fades.** The memorial (decision 52) and the titles' credit
  crossfade (decision 53) walk MODE 2's eight-colour brightness ladder with
  `&FE21` writes. Sixteen free colours have no such ladder, so both need a fade
  of their own — genuinely new work, and the only part of this that is.

## The panel and the HUD have to agree

The bar is drawn once and never redrawn; the score, the high score and the lives
are the only parts that move, and the runtime pokes HUD glyphs into eighteen
fixed cells of it (`hud_cell_lo/hi` in `src/bank3.asm`) — score at row 1 columns
7-12, high score at row 1 columns 27-32, lives at row 2 columns 17-22, all
including `PANEL_SHIFT`. Nothing in the picture says which eighteen those are,
so `check_hud_cells` says it: ink painted there is seen at boot and never again.

A **warning**, not a rule, and measured rather than assumed — the C64's own bar
leaves all eighteen blank and the Amstrad's paints all eighteen (decision 56),
so both are defensible and the game runs either way.

The CPC path keeps its **hard** assert, which is a different thing: its panel
image has the three life markers drawn in, and they must equal HUD glyphs 11
and 12 byte for byte. That is what proves the dither phase — every HUD cell
starts on an even pixel column and an even row, so a glyph's own `(x + y)`
parity is the panel's. It is not a matter of taste and stays an assert.

An earlier version of this check compared the C64 panel's markers against the
glyphs and fired every time. Two reasons, both worth writing down: the C64 panel
has **nothing** in those cells, and `HUD_PAIR_3` deliberately gives the glyphs a
white body where the ornament's colour RAM would give blue, so even where they
do coexist they are not meant to match on colour.

## The hit flash is derived from the art, not from a flag

Decision 59. `export_sprites.py`'s two flash LUTs recolour everything outside
`KEEP`, and `KEEP` used to be a per-source constant: the C64's three shared
colours, the CPC's transparency key alone. Hand-drawn art cannot be assumed to
hold to the C64's rule — blue may be a hull colour — so `derive_keep` asks the
art instead: if every frame is transparent, blue, white and at most one further
colour, the flash keeps blue and white exactly as the original does; otherwise
it takes the whole sprite.

This is why the seeded sheets reproduce the C64 build byte for byte and the
fallback arrives by itself the first time a frame needs it. `--cpc` derives the
transparency key alone on its own, which is what `CPC_KEEP` said by hand.

## Verified

* **The seeded sheets re-export byte for byte.** `git diff src/data/` is empty
  after `seed_art.py` and all three sources — PNG, `--c64`, `--cpc` — for
  `chars.bin`, `sprites0/1.bin`, `compiled.bin`, `compiled_zp.asm`, `panel.bin`
  and `hud.bin`, and for the four `-cpc` copies. This is
  the check that the PNG path adds and loses nothing, and
  `validate_art.py --roundtrip` runs it in one command: *all 256 characters and
  all 119 frames identical to the C64 conversion*.
* **The disc, file by file.** `ANDY`, `BANK1`, `BANK2`, `BANK3`, `LOADSC1/2`,
  `MUSIC` and `PANEL` are identical to HEAD's. `BANK0` differs only past
  `&BD5D`, which is code shifted by the palette change, and `Edge` in the seven
  bytes of bank-0 entry addresses that moved with it.
* **All eight flag combinations assemble**, `RELEASE` × `MUSIC_AKL` × `GFX_CPC`.
* `tools/verify_compiled.py` passes on both builds.
* jsbeeb, Master 128: loading screen, memorial fade, titles with the credit
  crossfade and the zoom scroller, and a game in play — all correct, with the
  palette coming from the file.
* The error paths were exercised deliberately, not assumed: a colour outside the
  palette, a half-width pixel, the transparency key on the character sheet and
  a not-yet-drawn cell all report cell and pixel and exit non-zero; three
  undrawn frames export identically to the C64 build through the fallback.

## Facts worth keeping

* **The starfield is in the art.** `src/bank1.asm` plots a star only where the
  play buffer byte reads exactly zero, so "empty space" has to stay logical 0.
  The C64 conversion has 23 all-black characters and `validate_art.py` prints
  the count against that, because painting them away would make stars vanish
  behind scenery that looks empty.
* **Collision is not in the art and cannot be painted.** It is bit 4 of
  `col_decode` per character number. A solid character repainted to look like
  open sky stays just as fatal — hence the line in the artist's brief.
* **beebasm will not `INCLUDE` inside a braced block.** `setup_display` is one,
  which is the mechanical reason `palette.asm` is included outside it; the
  reason it is in main RAM at all is the space argument above.
